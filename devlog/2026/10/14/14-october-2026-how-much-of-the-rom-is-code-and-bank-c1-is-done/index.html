2026-10-14

14 October 2026: how much of the ROM is code? And bank $C1 is done

Every progress figure on this site divides the code matched so far by the amount of code in the game. Until today that second number, 358,356 bytes, came from a one-off survey done at the start. Now that whole banks are matched, it could be checked, and it was wrong by a third.

What was counted as code

The biggest error is two banks, $CA and $CB, which the old survey credited with about 92 KB of code. They are the game's music. The sound driver keeps a table of 62 sample addresses and a table of 83 songs, and between them they cover all of $CA and nearly all of $CB. The old figure for $CA begins at the exact byte where the song data starts.

Bank $CC was the next largest: 27 KB claimed, about 4.4 KB actually code at the end of the bank. The rest is tables that the battle code reads. Ten more banks ($DE, $E4, $E5, $F5 to $F9, $FC, $FE) hold palettes, map tables, pointer tables and compressed data, and no jump or call from any matched or traced code leads into them.

Two pieces of real code are now counted separately, because they don't run as 65816 code where they sit in the ROM: the sound chip's own program in $C7 (7 KB, for a different processor), and a 26 KB compressed block in $C3 that the game unpacks into RAM and runs from there.

How it is measured now

For each bank, the count is the matched code (exact), plus the unmatched code that can be reached by following jumps and calls from matched code and the interrupt vectors, plus an allowance for code that can only be reached through jump tables nobody has decoded yet. The tool that does this was tested by hiding the source of a bank that is already matched and seeing how close it got. For $C0 and $C1 it came within 2–4%. For $C2, which still has a lot of unmatched code mixed in, it came out 17.6% low.

That last result matters for how to read the new figure. The estimate leans low, and a smaller total makes the percentage bigger. So the honest headline comes with a range.

An independent check reproduced every number, confirmed the sound tables and the code-free banks from the ROM itself, and asked for exactly that caveat to be stated plainly.

Where the re-survey left things

The game has about 240 KB of 65816 code, not 358 KB. main stood at 170,895 matched code bytes: 71.27%, with a likely range of 65–73% and the true figure more likely below 71% than above it. All 2,403 matched routines were independently verified.

Nothing was matched or unmatched by this change. The work done is the same; the measure is better.

Bank $C1 is complete

The last 2,982 bytes of $C1 are matched, so every byte of the battle engine's bank now comes from source. Most of it is the 57 target handlers that enemy behaviour scripts call to pick who an action hits: the party, the enemies, the enemy itself, the nearest or farthest, the lowest HP, everyone with a given status, a fixed slot, or a random pick. The rest is the bank's entry block (the battle's entry point and its service dispatcher) and a stretch at the end of the bank that holds cut-off copies of code from an older build, never run.

The handlers have bugs of their own. Target $05 can loop forever in one state, $08 never compares the first party member's HP, $1F stores its loop counter from the wrong register, and $38 stops clearing the list after its second entry. Review also turned up something subtler. Several handlers leave out "self" by comparing against a stored battler slot. On the enemy's own turn that slot is the enemy. In the pass that runs every enemy's script in turn, though, nothing sets it, so "self" there is whoever acted last. It took six review rounds to describe exactly when that slot holds what.

The equipment screen and the menu's drawing code

In $C2, 4,904 bytes: the menu's pad input, cursor and sound requests, and the draw-list interpreter that builds windows, text and numbers (with the play-time clock and item names and descriptions). One of the menu modes turned out to be the equipment screen. A table of slot names sits right next to it in the ROM: "Weapon", "Helmet", "Armor", "Accessory".

A Mode 7 scene and the white fades

In $FD, 4,515 bytes: two palette animations that fade or pulse colours toward white, a complete Mode 7 scene started by event command $FF $80-$8F (an iris window, a sprite bitmap drawn with rays, palette cycling), and the routine that uploads the field's animated tiles. Which scene in the game it is has not been traced yet. Two of the white fades write only one byte of each colour, so they change one channel and leave the rest of the colour as it was.

The decompressor and the jet bike race

The first 4,299 bytes of $C3 are the bank's kernel. The centrepiece is the decompressor, called from 42 places in the game. Its header now describes the packed format completely, and two reviewers each wrote their own decoder from that description and ran it over the ROM's packs. Every one unpacks cleanly. The largest pack, 26 KB at $C3:1313, unpacks to 34 KB of 65816 code at $7E:3000. A block of staff text in the same bank reads "JET BIKE RACE", so that module is the race against Johnny. The rest of the kernel is the services that module calls: a script interpreter, task lists, sprite builders, a bitmap scaler, and the window shapes (circles, wipes and four-sided shapes) that the field also uses.

The module itself is still raw bytes. Matching it would need a packer that rebuilds the exact compressed bytes, which is a project of its own.

The sound driver's 65816 side

Every sound and song request in the game goes through one entry point in $C7. That bank's 65816 code is now matched: 3,601 bytes that boot the sound chip, upload its program, and pass commands to it through four I/O ports. The handshake is written out step by step. The bank also holds a table of 83 songs and 62 instrument samples. The sound chip's own program, which runs on a different processor, is a separate job.

The rest of $FD

From $FD:A8A5 to the end of the bank, everything now comes from source: the fixed party and commands for one scripted battle, the animation lists for each location's tiles and palettes, and older copies of two routines that nothing runs. It is all data, so it doesn't move the code figure.

How a battle moves and draws

All of bank $CF's code is matched: 7,424 bytes. It is what runs every frame of a battle. One routine uploads graphics during the screen's blanking period, another steps everything else. Then come the movers that carry battlers and effects along lines, curves, arcs, circles and ellipses, or shake them in place. The sprite builder sorts every battler and effect by depth before it draws them, and the damage numbers bounce. When an enemy falls, a routine fades it out and takes it off the field.

Review found that two of these headers had their logic backwards. The objects that follow other objects are updated from the last one down, so a follower gets the old position of a lower-numbered leader but the new position of a higher one. The rule for hiding sprites at the screen edge doesn't hide them at all in one case: a sprite just off the left edge comes back partly visible. Both are now described as the code really behaves.

Setting up a battle, and the save files

The code at the end of $CC sets a battle up. Over several frames it uploads the battle graphics to video memory in stages, lays out the enemy names, and builds the list of who is fighting next to whom. It also has the helpers that reset an action's state between turns. Among them is a routine that returns before uploading its last two pieces, so the code that would upload them never runs.

From the end of bank $FF come the menu routines that $C2 calls. They build the tile sets for the menu font, step a wave effect, and draw a colour gradient. They also save and load the three save slots in battery-backed memory, with the checksum that guards each one. The check at boot that looks for valid save files writes its answer over the first byte of the play-time counter. The menu clears that counter right after, so nothing breaks.

The first part of $CD

$CD is the largest bank of code still unmatched, about 14 KB. Its first 5.8 KB are now matched. It is the battle's frame and screen work: the interrupt that runs once a frame and decides what to upload, the window wipe that opens and closes a battle, screen shake, the text boxes for battle messages and for the tech and enemy info panels, the routine that dissolves a defeated enemy pixel by pixel, and the scripted background effects on the third layer.

One header took five review rounds. The battle code's service dispatcher promises that every service hands the registers back as it found them, and that can only be checked for a service whose whole call tree is matched. Each round the matched part grew, and the list of which services still reach unmatched code went stale again. In the end the header lists, for each service, exactly which unmatched addresses it can reach. The reviewer checked that with a call-tree tracer, and it caught one path the first tracer had missed because it didn't follow branches into other routines.

Battle effects in $D1, and a lost palette upload

The code at the end of $D1 is matched: 6.4 KB of battle effects. It has the battle's own interrupt handlers, palette whitening, a background gradient that follows a battler's HP, window shapes (bands, boxes, waves, and four-cornered shapes drawn line by line), screen shake and bounce.

$CD and $D1 call each other constantly, so the two batches were matched side by side, each with stand-ins for the other. Merging them meant replacing those stand-ins with the real routines and settling about 70 RAM addresses that the two sides had named differently.

Review turned up a real bug in the game. At the end of a battle the code installs a second frame interrupt and waits for it. That interrupt writes the palette upload and the HDMA switch through the data bank the interrupted code was using, and while the battle-exit code waits, that bank is RAM. So in those frames the palette upload and the HDMA re-enable land in RAM instead of on the hardware. Only the writes that name the hardware bank directly reach it. It took two reviewers and three rounds to pin down exactly which writes get through.

Two of the window routines have a quieter side effect. Each 16-bit store to the WRAM data port also writes one byte to an address that mirrors a port of the sound chip.

Where that leaves things

main now stands at 213,667 matched code bytes: 87.87% of the surveyed code. The same caveat holds: the survey leans low, so the true share is more likely a little below that. All 3,036 matched routines are independently verified.

Next

The next part of $CD, the battle effect script's opcodes, is being matched now. After it come the rest of $CD, $CE, and the rest of the menu code in $C2.
