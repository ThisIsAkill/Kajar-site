Devlog

Notes on the Chrono Trigger matching decompilation project, one post per working day. Written in plain English — if you don't know 65816 assembly, check the Glossary first.

2026-10-08

8 October 2026: who can you hit? The target modes

The code that answers "who does this action hit?" for the battle menu is matched: a 33-entry table of target modes and the eighteen small routines behind it, plus the routine that puts a character into the ready queue. 1,033 bytes in 26 functions (session 43).

2026-09-24

24 September 2026: the cursor that draws itself

One big routine: BattleMenu_UpdateCursorOverlay, 828 bytes, the last stub in the command-menu neighborhood. Every frame, after input is processed, it decides what the pointing hand (or hands) on screen should look like, and where.

2026-09-22

22 September 2026: the tech and item lists, and the command menu is closed

The input handling for the tech list and the item list is matched, the last two submenus still holding stubs. Every input handler in the battle command menu is now matched code. 637 bytes in 15 routines, the last two increments of session 41.

Continue reading →

2026-09-19

19 September 2026: the battle command menu, from dirty flag to committed action

The biggest single day so far: 1,478 bytes in 22 routines, all in bank $C1's battle command menu. It now runs as matched code from the gate that decides whether to redraw the menu, through controller input and confirm, to the 8-byte action record the battle engine executes. This is the first stretch of session 41, worked in eight increments.

2026-08-14

14 August 2026: opening bank C1, from the math helpers to the battle windows

Bank $C1, the battle engine, is open. In one day it went from an empty file to 4,085 matched bytes: math and number formatting, the battle status bar and all its callees, the item and tech list renderers, and the per-frame window upkeep. 33 functions over sessions 34 to 40, plus a root-cause fix in the disassembler.

2026-08-12

12 August 2026: the sprite-init system closes, and a first look at bank C1

The triple-slot routines, the dispatcher layer above the sprite-slot cluster and the animation queue that drives it are all matched, so the sprite system from $C98A to $E129 is one continuous run of matched code. Then a scouting pass over bank $C1, the battle engine. 3,509 new bytes in 10 functions (sessions 31 to 33).

11 August 2026: the sprite-slot cluster takes shape, and an honest progress number

Five body routines of the sprite-slot init cluster are matched, then the triple-slot dispatch. In between, the progress number gets a real denominator: matched code against the game's code, not against the whole 4 MB ROM. 2,377 new bytes in 7 functions (sessions 29 and 30).

One routine today, Sub_CB3A (162 bytes), the gate at the start of every sprite-slot init routine. Scoping around it corrected yesterday's picture of the call chain and mapped a new cluster at $CB3A–$D800.

9 August 2026: the Sub_E12A cluster closes, and the slot allocators

All six callees of Sub_E12A are matched in one pass, which completes the sprite init arc. Then the three sprite-slot allocators that sit just before it: 1,169 new bytes in 9 functions (sessions 26 and 27).

2026-08-07

7 August 2026: the last mode handler, screen transitions, and the sprite init pass

The $0C76 mode dispatch is closed with the default handler. Then the whole screen-transition path, from fade-out through scene save and restore to fade-in, is matched, two early labels are corrected, and the 1,034-byte sprite init pass Sub_E12A goes in: 2,568 new bytes in 15 functions over sessions 21 to 25.

2026-08-06

6 August 2026: the engine spine, the whole sprite system, and the mode handlers

The longest day so far, seventeen sessions (4 to 20) in bank $C0. The game loop and its per-frame reset are matched, then the complete sprite system, from the VBlank handler down to every renderer and init helper, then the head of the per-frame state machine and all five of its named mode handlers: 9,542 new bytes in 32 functions.
