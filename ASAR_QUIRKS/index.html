asar 1.91 Quirks

Surprises encountered during this project. Future contributors: read this before spending an hour debugging a byte offset.

1. Named equate → STA generates LONG mode

Symptom: STA INIDISP emits opcode 8F (STA long, 4 bytes) instead of 8D (STA abs, 3 bytes). Every instruction downstream shifts by 1 byte.

Cause: When the operand is a named equate (e.g. INIDISP = $2100), asar promotes to 24-bit addressing regardless of the value's size.

Fix: Force abs mode with the .w suffix:

65C816 Assembly
STA.w INIDISP    ; $8D 00 21 — correct (3 bytes)
STA.w NMITIMEN   ; etc.
This applies to all hardware register writes where the register is defined as a named constant.

2. STX EquateName — "Unknown command"

Symptom: STX A1T7L (where A1T7L = $4372) produces an asar error.

Cause: asar 1.91 does not accept named equates as the operand for STX.

Fix: Use the raw hex literal:

65C816 Assembly
STX $4372        ; works fine

3. STA $0001,X → dp,X mode (not abs,X)

Symptom: STA $0001,X emits opcode 95 (dp,X) instead of 9D (abs,X). The value $0001 fits in 8 bits so asar defaults to direct-page indexed.

Fix:

65C816 Assembly
STA.w $0001,X    ; forces abs,X: $9D 01 00
Comes up in the PostVBlank OAM-fill loop.

4. BRL label stores the raw operand, not a target address

Symptom: BRL SomeLabel works fine. BRL $XXXX stores $XXXX as the branch offset directly, not the absolute address.

Cause: By design in asar. The BRL operand is a signed 16-bit offset from the next instruction, not an address. When you write BRL $XXXX, asar stores $XXXX literally.

Context in this project: VBlankHandler contains BRL $B193. That $B193 is the raw signed offset that lands at PostVBlank ($C0:B271) — it is NOT the address $B193.

Fix: When matching a BRL, extract the signed 16-bit operand from the ROM bytes and use it directly:

65C816 Assembly
BRL $B193        ; raw offset, not an address label
Using a label reference like BRL PostVBlank would likely produce a different offset.

5. JSR EquateName — "Unknown command"

Symptom: Similar to the STX issue — JSR SomeEquate fails.

Fix: Define a label stub at the target address with org:

65C816 Assembly
org $C0B309
Sub_B309:        ; no bytes emitted — just a label for JSR to resolve

; ... later, or elsewhere:
    JSR Sub_B309 ; resolves correctly to $B309

6. LDA #$7F in M=0 context: ROM uses 2-byte form, asar emits 3 bytes

Symptom: LDA #$7F in a 16-bit accumulator (M=0) context assembles as $A9 $7F $00 (3 bytes: immediate sign-zero-extended to 16 bits). If the ROM contains the 2-byte sequence $A9 $7F followed by an unrelated byte, make diff will show a 1-byte shift.

Cause: With M=0, LDA immediate is a 3-byte instruction. The assembler always emits the full 16-bit operand even if the value fits in 8 bits.

When it occurs: The ROM sometimes stores $A9 $7F (2 bytes) intending the next byte to be the following instruction, not the high byte of the immediate. This happens when the compiler originally ran in M=1 mode or used an 8-bit trick that asar doesn't replicate automatically.

Fix: Emit the raw bytes directly:

65C816 Assembly
db $A9,$7F        ; forces the 2-byte sequence in M=0 context
Do not write LDA #$7F when in 16-bit accumulator mode and the ROM has only 2 bytes here.

Discovered: session 26, during Sub_E12A Phase 1 matching (LDA #$7F / STA $D2).

7. SBC #$NNNN / ADC #$NNNN in M=0 context: wrong encoding

Symptom: SBC #$0040 (or ADC #$0040, etc.) in a 16-bit accumulator (M=0) context may assemble to the 2-byte M=1 form ($E9 $40) rather than the correct 3-byte M=0 form ($E9 $40 $00). This causes a 1-byte shift and a cascade of mismatches downstream.

Cause: asar 1.91 does not always track the M flag correctly across REP #$20 when choosing immediate operand width for SBC and ADC.

When it occurs: Any SBC #$xxxx or ADC #$xxxx in M=0 (16-bit A) context, especially when the upper byte of the immediate is $00 (i.e., the value fits in 8 bits, making the 2-byte vs 3-byte ambiguity matter).

Fix: Emit the raw bytes directly, same pattern as the LDA #$7F workaround:

65C816 Assembly
REP #$20                        ; M=0
; instead of: SBC #$0040        (may emit 2 bytes)
db $E9,$40,$00                  ; SBC #$0040 — explicit 3-byte M=0 encoding
; instead of: ADC #$000E        (may emit 2 bytes)
db $69,$0E,$00                  ; ADC #$000E — explicit 3-byte M=0 encoding

The opcode bytes are: $E9 = SBC immediate, $69 = ADC immediate; followed by the 16-bit little-endian operand.

Discovered: session 35 (BattleMsg_FormatNumberDigits); applies to all 16-bit SBC/ADC immediates in M=0 context. Confirmed again in session 36 (BattleUI_BuildStatusBarFrame).
