Field event scripts

Every object on a field location (people, doors, the party members themselves) is driven by a byte-code script in the location's event data. The interpreter and most of its opcode handlers are in bank $C0 and matched; the opcode table itself (Evt_OpcodeTable, $C0:5D6E, 256 words) is not yet, and a number of handlers still have no name (see What is not matched yet).

See also: Frame cycle and NMI, Engine core, Sprites & objects.

Objects, functions and levels

LocLoad_Unk56D4 ($C0:56D4), the last location-load step, unpacks the event data; LocLoad_CheckEvtData checks it and stops the game on a colour (Sys_HaltWithColor) if it is bad. The data starts with a function table: 16 function offsets per object (32 bytes per object at Evt_Data + slot × 16, the slot being the object number × 2).

Evt_InitObjects ($C0:5709) resets the per-object tables for the location's Evt_ObjCount objects and runs each object's function 0 (its init function) up to opcode $00. Evt_RunObjInit ($C0:597D) does the same for one object; Party_ReinitIfChanged uses it for the character objects after a bank-$C2 round trip.

Each object runs at a level (Obj_Unk1C00), 7 after its init function. The function-call banner reads lower levels as more urgent, "probably": a call only interrupts an object running at a higher level. A call saves the interrupted script position in a per-level table (ObjX_Unk7F0580), and Evt_Op00_Return ($C0:5F74) resumes the first saved position above the level that ends. The action button (Field_ActionButton → Evt_StartTargetFunc1) starts function 1 of the object found in front of the leader; Evt_StartTargetFunc2 is the touch counterpart (function 2).

The scheduler

Scripts run from Field_EndOfFrame, once per frame, in two steps ($C0:59D9–$C0:5AC4):

  1. Vblank_Unk59D9 counts down every object's script timer (Obj_Unk1001, reloaded from Obj_Unk1000, 4 at load) and queues the objects whose timer ran out (kind-0 objects at the head of the list, others at the tail).
  2. Vblank_ReadScanlineCounters runs the queued objects while the frame still has time: before each object it reads the PPU's V counter and stops once it is at ObjQ_Unk69 ($48 from Scene_PostLoadInit) or more but below line 240.
  3. Evt_RunObjScriptSteps ($C0:5A93) runs one object: up to Field_Unk68 opcodes (5 from load) through Evt_OpcodeTable.

Every handler is entered with Y = its opcode's offset in the event data and returns X = where the script goes on, with C=1 to run the next opcode in this run or C=0 to stop the object until its next run. A handler that returns its own position with C=0 runs again next time: that is how waits and moves in progress work. The two scheduler routines keep their Vblank_ names because verified callers use them; their headers suggest Obj_QueueScripts / Obj_RunQueuedScripts.

The unused opcodes ($01, $3A, $3D, $3E, $45, $46, $6E, $70, $74, $78, $79, $85, $86, $93, $9B, $A2–$A5, $BE, $BF, $C5, $C6, $DB, $E9, $EF, $F5–$F7, $FB–$FD) all point at Evt_UnusedOpcode ($C0:5F6E), which stops the game on the colour Halt_ColorBadOpcode.

Operands follow common conventions: "slot" is an object × 2; "p" is 0, 2 or 4 for a party member; "a"/"b" name event words at Evt_Unk7F0200 + a × 2 (a byte stored into one goes to its low byte only); "m" is an address in bank $7F (Evt_Mem7F + m); "ptr" is a 3-byte long address. Jump distances are unsigned bytes counted from the operand itself, forward for every jump but $11. A condition opcode goes on with the next opcode when its condition holds and jumps when it does not.

Movement

The movement opcodes set up a timed move and then return their own position with C=0 until it is done, keeping Obj_Unk1A80 nonzero meanwhile. They lean on the object motion code: Obj_CalcDirection ($C0:ABA2, an angle with 256 steps per turn from a 32×32 table), Obj_SetVelocity and Obj_SetVelocityChecked (steps from the angle and speed with the hardware multiplier), and Obj_MoveStep / Obj_MoveStepFree, which the per-frame object pass Vblank_UnkA810 runs. Evt_Op7A_ArcToTile moves an object along an arc to a tile ("probably a jump", per its header), with a gravity operand.

Messages

The message opcodes ($B8, $BB, $C0–$C4) wait until Field_Unk29 is 0, start Field_Unk1F87's sequence with a number, the object and a pointer set by Evt_OpB8_SetMsgPtr, then wait for it to finish. Reading this as a text message with a choice cursor is, per the banner, "an inference from those uses, not traced through Field_Unk1F87" (which is not matched).

Quirks kept

The handlers keep the original's oddities, each documented in its header. A few: Evt_Op00_Return's level search has no upper bound; Evt_Op6F_ShrVarByte treats a count of 0 as 256 shifts; the comparison numbers of opcodes $12–$16 and the bit numbers of $63–$66 are not masked; Evt_OpB6_FollowPc is missing a CLC; Evt_InitObjects fills three bank-$7F tables and then clears them again in its next step.

What is not matched yet

  • Evt_OpcodeTable itself ($C0:5D6E–$C0:5F6D).
  • The handlers with no name yet: $29–$2C, $2E, $2F, $32, $33, $57, $5C, $62, $68, $6A, $6C, $6D, $7C–$7E, $80–$84, $87–$8E, $90, $91, $C7–$DA, $DC–$E8, $EA–$EE, $F0–$F4, $F8–$FA, $FE, $FF (from NEXT.md, which lists the code at $C0:326C–$C0:353E and $C0:3711–$C0:4CD5 as next).
  • The party-control callees Party_Unk9E29, Party_UnkA26B, Party_UnkA2CE (the leader's step log and the members' follow, probably).
