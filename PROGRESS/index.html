Session 41 (eighth and final increment): BattleMenu_CommitAction (308 B) + BattleMenu_ConsumePartnerSlot (30 B) + BattleMenu_TargetNext (26 B) + BattleMenu_TargetPrev (22 B) = 386 bytes. Session 41 (ninth increment, new day): BattleMenu_TechListInput (73 B) + BattleMenu_TechConfirm (38 B) + BattleMenu_TechListCancel (30 B) + BattleMenu_TechListPrev (71 B) + BattleMenu_TechListNext (73 B) = 285 bytes. Closes the entire tech-list-input stub. TechListInput is the per-frame dispatcher; TechConfirm hands off to targeting the same way ChooseAttack does; TechListCancel restores the saved cursor/scroll and returns to the main menu; TechListPrev/Next are the interesting pair — moving the tech cursor isn't a simple increment/decrement, because unavailable techs (per-slot availability byte $1CDB) must be skipped, and skipping can require the visible window to scroll. Both routines walk step-by-step to the next/previous available entry, then replay that same step count against the (cursor row, scroll offset) pair to keep the two in sync, scrolling a row at a time whenever the row would go out of the visible 0-2 range. Closes the entire tech submenu now that item is the only list-input handler left as a stub.

Session 41 (tenth and final increment): BattleMenu_ItemListInput (91 B) + BattleMenu_ItemConfirm (67 B) + BattleMenu_ItemListCancel (17 B) + BattleMenu_ItemCursorUp (22 B) + BattleMenu_ItemCursorDown (26 B) + BattleMenu_ItemListPageDown (27 B) + BattleMenu_ItemListPageUp (20 B) + BattleMenu_ItemListRefresh (22 B) + BattleMenu_ItemListScrollUp (30 B) + BattleMenu_ItemListScrollDown (30 B) = 352 bytes. Closes the entire item submenu — and with it, every submenu-input handler in the whole command-menu subsystem (main/tech/item/target-select) is now matched. Architecturally simpler than the tech list: items have no per-slot "unavailable, skip it" flag during cursor movement, so up/down just move the cursor and call a scroll helper at the row-0/row-2 edges. Two implementation details worth flagging: (1) BattleMenu_ItemListScrollUp has a genuinely odd redundant double-branch — two consecutive BEQs testing the same unchanged zero flag, where the second one's target can never actually be reached, since getting there at all requires the first check to have already found the flag clear; reproduced exactly. (2) BattleMenu_ItemListPageDown/PageUp don't call the render routine directly — they JSR into a sub-entry point inside ItemListScrollDown/ScrollUp (the exact address of the internal JSR BattleMenu_RenderItemListRows instruction), reusing that shared render+indicator-invalidate tail rather than duplicating it. Required exposing that entry point as a real global label rather than a local .dot label, per the project's known asar quirk #6 (a new global label resets local-label scope, so a label referenced from a different routine's scope can't be local). Also corrected two stale/incorrect inline comments in session 39's BattleMenu_RenderItemRow — $1580,X/$1583,X were mislabeled "unconfirmed-animation flag" and "item ID" respectively; BattleMenu_ItemConfirm's clear indexing this session ($1580=id, $1583=quantity) made the error obvious.

Session 42: BattleMenu_UpdateCursorOverlay (828 B) — the last stub in the command-menu neighborhood, now matched; $C1:1320–$C1:1B18 is one continuous matched span. A four-way per-frame dispatcher: no active PC (hide cursor), tech list (single cursor, or a 2–3 sprite cluster over the caster plus dual/triple-tech partners decoded from the nibble-packed $9EE7), item list (scroll-arrow glow + row-highlight quad, each cached against its last-drawn value so a VRAM upload is only queued when something changed; down arrow uses attr $A9 vs the up arrow's $29), and target select (single cursor with an enemy info-panel dispatch through two cross-bank message vectors, or a multi-target sweep that draws 3 selection-list entries per frame into the 4 available cursor OAM slots and resumes next frame from $960B, wrapping after 6 — i.e. cursors alternate between target groups across frames). The battler-screen-position idiom ($1D0C,X/$1D23,X base + $9708,X/$9713,X live offset − $10) appears six times, always inlined.
