Bank Map

Per-bank breakdown of the ROM. Update as regions are identified and matched.

ROM: US 1.0, HiROM, 4 MB ($400000 bytes), 64 banks × 64 KB each. Banks $C0–$FF are the canonical addresses; $00–$3F are shadows of their $8000–$FFFF halves. Banks $80–$BF mirror $00–$3F for speed-select purposes.

BattleMenu_DequeueReadyBattler closes out the last stub callee referenced by the menu dirty-flag gates matched at the start of today's session. Dequeuing restores that battler's saved menu-cursor position ($A863/$A866 → $95DF/$95EB, the same save/restore pair BattleMenu_TechListCancel uses), marks the slot present in the roster by writing its own index into $A6D9,X (an identity-map — this project has seen $A6D9,X used as a presence/validity check via BMI elsewhere, e.g. BattleMenu_CycleActivePcPrev), forces a command-window reload sentinel, shifts the queue down one slot, and — if no PC was already active — promotes the newly-dequeued battler to active.

Immediately adjacent at $C11BAA sits BattleMenu_RemoveBattlerFromReady (service 2 of the $C10045 cross-bank service-dispatch API first documented back when Bank $C1 was opened) — the inverse operation, thematically, and matched right after in the same session (see below).

Ready-Battler Remove ($C1:1BAA–$C1:1C39) — session 41 (final increment)

BattleMenu_RemoveBattlerFromReady is service 2 of the $C10045 cross-bank service-dispatch API, and the structural inverse of DequeueReadyBattler just above it: instead of pulling a battler into the active state, it takes one out, whether that battler is currently sitting in the 3-deep ready queue or is the actively-displayed menu PC.

The queued case reuses a familiar shape — scan the queue for a match, then shift everything after it down by one — generalized from DequeueReadyBattler's always-shift-from-zero version to start from wherever the match was found. The active-PC case is meatier: if the battler being removed isn't the one currently on screen, it's a quiet removal (clear its roster slot, force a redraw). If it is the displayed PC, the routine also cancels any open submenu or target-selection state, then walks the roster looking for another valid slot to promote to active — or, if none exist, explicitly marks "no active PC."

This routine reproduced the exact same class of bug as BattleMenu_BuildTargetList earlier in the session: an early draft put a one-time LDA $80 inside the queue-scan loop instead of before it, which shifts where the loop's branch target sits and changes the branch's offset byte. Two occurrences of an identical mistake in one sitting is a pattern, not a coincidence — worth remembering that a single-byte make diff mismatch landing on what looks like a branch instruction, near a loop, is a strong signal to check whether a setup instruction got nested one line too deep.

Target-Select Input ($C1:1561–$C1:1619) — session 41 (seventh increment)

BattleMenu_TargetSelectInput is the per-frame input handler active whenever $9609 (target-select mode) is nonzero — reached from BattleMenu_ProcessInput's very first branch, and entered by BattleMenu_ChooseAttack back in the confirm-dispatch cluster. Every call rebuilds the target list from scratch via BattleMenu_BuildTargetList, then either cancels (no valid target found, or the cancel button) or polls for confirm/cycle-target input.

The cancel path is the meatier half: it restores whichever submenu was open before targeting started ($A86B), and — depending on whether that was the tech list or item list — either just re-flags the tech window active or fully reloads the $180-byte item-window graphic (ItemBoxBattles, the same ROM data BattleMenu_OpenItemList uses). Both paths converge on a shared cursor-highlight update: OR the OAM high-table byte with $55 and set four cursor-sprite X-positions to $F0.

The confirm/cycle path is comparatively simple — check $EE bits $C0 for confirm (tail-jump to BattleMenu_CommitAction, matched separately below), or $EF bits for cycling the target selection forward/backward (BattleMenu_TargetNext/TargetPrev, also matched below) — unless $960C's target-all flag is set, in which case cycling is disabled entirely.

A genuinely dead 18-byte block. Between the tech-return and confirm/cycle sections sits a near-exact duplicate of the item-graphic copy loop: same TDC/TAX/copy/INX/CPX #$0180 shape, but its loop-continue BNE targets the confirm/cycle section's entry point instead of looping back on itself. The practical effect is that if this block ever executed, it would run exactly one iteration before falling out of the "loop" into unrelated code — it's not a working copy at all. More importantly, nothing in the routine's actual control flow reaches it: every path that could have fallen into it branches past it with an unconditional BRA instead. This is the first genuinely dead block (as opposed to a single stray byte, like session 39's dead RTS) found in Bank $C1. Reproduced byte-for-byte as unreachable code, per the project's standing policy of matching the ROM exactly rather than only the parts that still do something.

Command-Commit Cluster ($C1:161A–$C1:179B) — session 41 (eighth and final increment)

BattleMenu_CommitAction is the routine every confirm path in the entire command-menu neighborhood ultimately reaches — attack today, and tech/item once those submenus are matched (BattleMenu_TargetSelectInput's confirm branch tail-jumps straight here). It's the largest single routine matched in this whole cluster (308 B), and it's where a player's menu selections finally turn into a concrete battle command.

The shape is a three-way dispatch on $95DB (attack/tech/item) that fills in type-specific fields, followed by a shared tail that all three converge on. Attack is trivial — just a type flag and "no id" sentinel. Tech is the most involved: it optionally saves the menu cursor position, then — critically — "consumes" the partner battler(s) for dual- and triple-techs via BattleMenu_ConsumePartnerSlot, once for the primary partner (low nibble of $9EE7) and again for a second partner if the high nibble indicates a triple-tech. Item decrements the item's stock count and clears the item-list scroll position.

The shared tail builds an 8-byte command record at $93EE plus an offset resolved through the same $CCFAF0 slot-to-sprite-index lookup table ConsumePartnerSlot also uses — type byte, a flag byte, submenu type, target, and the tech/item id pair — increments the queued-command count, then clears the confirming PC's roster slot and searches for another valid slot to promote to active, reusing the exact same scan-and-fallback shape BattleMenu_RemoveBattlerFromReady used earlier today.

BattleMenu_ConsumePartnerSlot itself is a tight 30-byte leaf: mark the given slot's roster presence gone, decrement the active-PC count if it was currently active, and clear the "queued" bit of its sprite flag byte. BattleMenu_TargetNext/TargetPrev are D-pad cycling helpers for the target cursor ($9614), structurally identical to BattleMenu_CycleActivePcPrev/Next from earlier in the session — advance/decrement with wraparound, skip invalid candidate-list entries. TargetPrev doesn't even need its own RTS; it falls straight through into the already-matched Battle_ZeroResultEE since the two are adjacent in ROM.

This closes the entire span from $C1:161A to $C1:179B, connecting directly into Battle_ZeroResultEE — meaning the whole neighborhood from the menu dirty-flag gate ($C1:10E3) through target confirmation is now one continuous matched region, apart from the two remaining submenu-input stubs (TechListInput, ItemListInput, the former closed in the next session — see below) and BattleMenu_UpdateCursorOverlay.

Tech-List Input Cluster ($C1:1320–$C1:143C) — session 41 (ninth increment)

BattleMenu_TechListInput is the per-frame dispatcher for the tech submenu, computing the highlighted tech's list index (scroll position plus cursor row) before polling pad-edge bytes for confirm, cancel, and up/down. BattleMenu_TechConfirm hands off to targeting the same way BattleMenu_ChooseAttack does — set a target mode, build the target list, enter target-select mode if a valid target exists. BattleMenu_TechListCancel is the smallest of the five: restore the saved cursor/scroll pair and return to the main menu.

BattleMenu_TechListPrev and TechListNext are the pair worth slowing down for. Moving the tech cursor isn't a plain increment or decrement, because some techs in the list are unavailable (insufficient MP, not yet learned, etc. — tracked via a per-slot availability byte at $1CDB) and have to be skipped over rather than landed on. Both routines walk one step at a time from the current list index looking for the next available entry, counting how many steps that took — then replay that same step count against the separate (cursor row, scroll offset) pair that actually controls what's drawn on screen, scrolling the visible window by one row at a time whenever the cursor would go outside the visible 0–2 range. It's a two-coordinate-systems problem (list index vs. screen position) solved by counting the distance in one and walking it in the other, and it's structurally identical between the "up" and "down" directions apart from which way the walk goes and which end of the list bounds it.

This closes the tech submenu entirely — BattleMenu_ItemListInput (matched immediately after, see below) was the only remaining submenu-input stub.

Item-List Input Cluster ($C1:143D–$C1:1560 + $C1:17A1–$C1:17DC) — session 41 (tenth and final increment)

BattleMenu_ItemListInput mirrors TechListInput's dispatcher shape (confirm/cancel/up/down via the same pad-edge bit tests) with two extra branches: $EE bits $20/$10 let the player page the whole list up or down 3 rows at once, and a check of $A0D0 triggers a full re-render when some other part of the engine has flagged the display stale. BattleMenu_ItemConfirm is structurally close to BattleMenu_TechConfirm — resolve a record index, reject if unusable, then hand off to targeting — but item records are a flat array ($1580, 5-byte stride: id/target-mode/flags/quantity + one padding byte) rather than the tech system's bitmask-based availability check.

The interesting architectural difference from the tech list shows up in cursor movement. Techs need step-counting-and-skip logic because some entries are unselectable; items don't have that problem (unusable items are presumably still just... items — the render routine handles greying them out, but the cursor still lands on them). So BattleMenu_ItemCursorUp/CursorDown are almost trivial: move the row, and only call out to a scroll helper (ItemListScrollUp/ScrollDown) when the cursor is already at the top or bottom of the visible window.

A sub-entry-point pattern, reused from bank $C0. BattleMenu_ItemListPageDown/PageUp don't call the render routine directly — they set the scroll position themselves, then JSR into the middle of ItemListScrollDown/ScrollUp, landing exactly on the internal JSR BattleMenu_RenderItemListRows instruction and reusing everything after it (the render call plus the scroll-arrow indicator writes) as a shared tail. This is the same "call into another routine's tail as a mini-subroutine" trick already seen in bank $C0's Sub_1BA7 (an alternate entry into Sub_1B90). Because the entry point is referenced from a different routine's scope, it has to be a real global label rather than a local .dot label — a direct application of the asar local-scope-reset quirk this project has documented before.

A genuinely redundant branch. BattleMenu_ItemListScrollUp opens with two consecutive BEQ instructions testing the exact same (unmodified) zero flag. The first one's target is reachable; the second one's isn't — by the time execution reaches the second check, the first check has already proven the flag clear, so the second BEQ can never fire. It's not dead code (the bytes execute every single call), just a dead branch — a distinction from the fully-unreachable block found in BattleMenu_TargetSelectInput earlier this session. Reproduced exactly either way.

A correction to session 39. Working out BattleMenu_ItemConfirm's exact field layout ($1580=id, $1583=quantity) revealed that BattleMenu_RenderItemRow's inline comments — written back in session 39, before this part of the item system was understood — had those two swapped (labeling $1583,X "item ID" and $1580,X "unconfirmed-animation / display flag"). Fixed both comments; no byte changes, since comments don't affect matching.

This closes the item submenu, and with it, every submenu-input handler in the entire command-menu subsystem. BattleMenu_UpdateCursorOverlay is now the only remaining single-routine stub in this whole neighborhood.

Cursor Overlay ($C1:17DD–$C1:1B18) — session 42

BattleMenu_UpdateCursorOverlay runs once per frame at the end of the menu rebuild chain and draws whatever cursor belongs on screen. It is effectively four routines behind one dispatcher: no active PC → hide the 4 main-cursor OAM slots ($0700–$070F, visibility bits in $0900); tech list → the normal single cursor, or for a dual/triple tech (tech id ≥ $39) one sprite over the caster and one over each partner, partners decoded from the nibble pair in $9EE7 ($F = none); item list → change-tracked redraws of the scroll arrows ($0EFC/$0FFC, cached in $9920) and the 4-tile row highlight ($CCFAE9 pointer table, cached in $991F), queuing JSL $CFFD6A only if either changed; target select → a single cursor (with an enemy info-panel dispatch through JSL $CD0030/$CD002D in the main Attack menu, gated by the per-enemy table $E1DE80) or a multi-target sweep.

The multi-target sweep is the notable piece: with only four cursor sprites, it draws three selection-list entries per frame, saves its position in $960B, and resumes there next frame, wrapping after six — so the cursors alternate between target groups across frames rather than all being drawn at once.

Every cursor placement uses the same inlined idiom: $1D0C,X/$1D23,X (base origin, shared with DrawCursorSprites) + $9708,X/$9713,X (per-battler live offset, X = any of the 11 battler slots) − $10.

With this matched, the span $C1:1320–$C1:1B18 is continuous and the command-menu subsystem has no stubs left.

Target-Mode Layer ($C1:1B19–$C1:1B54 + $C1:1FDD–$C1:2331 + $C1:27C5–$C1:283C) — session 43

BattleMenu_EnqueueReadyBattler (service 1 of the $C10045 API) is the entry side of the ATB-ready queue that DequeueReadyBattler drains: it skips battlers already in the roster, sets bit 7 ("waiting for command") of the battler's $93EE flag byte, appends to $95D6+count, resets the cursor row to $9916,X, and plays SPC command $19 with sound $42.
