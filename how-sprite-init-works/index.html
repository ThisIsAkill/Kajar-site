How Sprite Init Works

A technical reference for the Chrono Trigger SNES sprite subsystem, as recovered from byte-exact matched code in bank $C0. This page describes the system as it works, not the history of matching it.

Overview

Every display frame the VBlank interrupt fires and calls PostVBlank. PostVBlank walks a 63-entry sprite descriptor table and, for each active slot, calls Sub_B309 to build the SNES OAM buffer entry. Sub_B309 first gates the sprite through Sub_B701 (which checks whether the sprite is ready and handles its init/render split), then writes position bytes from the staging buffer into the hardware OAM range.

Sprite types

The sprite type lives in bits 0–1 of the byte at $7E:1201,X (where X is the sprite descriptor index).

Type OAM bytes Palette iters Tile count Renderer
0 1 4 ~4 Sub_B788
1 2 8 ~8 Sub_B309 direct
2 3 12 ~12 Sub_B309 direct
3+ 6 24 ~24 Sub_C73A

Sub_B309 sizes its OAM write, its WRAM advance step (ADC #$0010/$0020/$0030/$0060), and its palette loop count from the type field. Type 3+ has its own renderer (Sub_C73A) that Sub_B701 tail-jumps to directly via BRL.

State byte and the high/low-state split

The state byte at $7E:1B00,X controls what Sub_B701 does with a given sprite slot. The encoding is:

Value Meaning Action
$00 Inactive Carry set, skip
positive, below threshold Partially initialised Carry set, skip
positive, at/above threshold Ready for high-state init Run high-state init helpers, set $80
negative (bit 7=1, bits 0–6 nonzero) Staging buffer populated Run low-state init (re-read staging)
exactly $80 Fully initialised Run renderer

The threshold varies by type: type 1 requires state ≥ 2; types 2/3+ require state ≥ 3.

What "high state" means: the staging buffer is empty or stale. The init helper reads raw animation data from ROM/WRAM tables and writes it into the $7F:4B00 staging buffer. This is the expensive path — it copies source bytes, applies Y clamping, and populates every field.

What "low state" means: the staging buffer was already populated by a previous high-state pass. The init helper reads Y data directly from the staging buffer rather than from the raw table. This saves a table lookup cycle and produces slightly different branch logic (see Y-clamp orderings below).

Type 0 does not have a separate low-state init helper. When a type-0 sprite is in state $80, Sub_B701 calls Sub_B788 (the renderer) directly.

The staging buffer ($7F:4BXX)

The staging buffer lives in bank $7F, at base address $4BC0. Each sprite uses an 8-byte stride indexed by gfx_index (loaded from $7E:1700,X):

Offset from $4BC0,gfx_index Width Written by Contents
+$00 8-bit B788, B8CA, C6E7 Tile X low byte
+$01 8-bit B788, B8CA, C73A Tile Y position (clamped)
+$02 16-bit B788, B8CA Raw X offset (copied from $4802,X)
+$04 8-bit B8CA Raw Y source (copied from $4804,X)
+$06 16-bit B8CA Extra 16-bit field (copied from $4806,X)

Sub_B309 reads from the staging buffer ($7F:4F00,X for OAM bytes) when building the hardware OAM entry. The palette copy loop reads $7F:4BC0,X via WMDATA ($2180, accessed through the DP=$2100 trick).

The region $7F:4F00 holds the OAM position bytes (1–6 depending on type). Region $7F:4BC0 holds the palette data. These are separate sub-ranges of the same bank-$7F staging area.

OAM buffer ranges

The engine uses three independent OAM ranges in WRAM, each with its own write-head pointer:

Range Write-head pointer WRAM bounds WRAM dest pointer
1 $7B $08A0–reset $01DB
2 $7D $0900–reset $01DD
3 $7F $0770–reset $01DF

Bits 2–3 of $7F:0F80,X select the range for each sprite. PostVBlank fills any OAM slots between each range's write-head and its ceiling with Y=$E0 to park them off-screen.

Sub_B309 uses the DP=$2100 trick to write OAM data: it saves the current DP (PHD), loads $2100 into A, transfers to DP (TCD), and then uses direct-page-addressed stores to hit PPU registers like WMADDL ($2181). At return it restores DP via PLD.

Init pass 2: the $0BC0 entity table

After any high-state init helper runs, Sub_B701 calls a pass-2 helper to mark the sprite's slot in the entity table at $7E:0BC0. The helpers search the table linearly for the current sprite's descriptor index ($6D), then write $80 to the matching entry (and adjacent entries for multi-slot sprites).

Helper Search length Bytes marked For type
Sub_E9E2 4 entries 1 byte: $0BC0,X 0
Sub_E9FF 3 entries 2 bytes: $0BC0,X, $0BC1,X 1
Sub_EA1F 2 entries 3 bytes: $0BC0,X, $0BC1,X, $0BC2,X 2/3+

All three follow the same structure: SEP #$10 (8-bit X), LDX $6D / LDX #$00 (reset counter), loop with LDA.w $0BC0,X / CMP $6D / BEQ found / INX / CPX #limit / BNE loop, then REP #$10 / RTS on no-match or after marking on match. The number of bytes marked equals the number of OAM bytes the sprite type uses.

Type/state matrix

Which init helper gets called for each type and state:

Type High-state init Pass 2 Low-state init Renderer
0 Sub_B8CA Sub_E9E2 (none — state goes $80 → Sub_B788) Sub_B788
1 Sub_BCDC Sub_E9FF Sub_BA65 Sub_B309 direct
2 Sub_C2BF Sub_EA1F Sub_BFF2 Sub_B309 direct
3+ Sub_C2BF Sub_EA1F Sub_BFF2 Sub_C73A

Types 2 and 3+ share the same init helpers. Type 3+ diverges only in the render path: Sub_B701 tail-jumps to Sub_C73A via BRL instead of returning to Sub_B309's OAM write code.

Y-clamp orderings

All the sprite routines that write tile Y positions apply a three-way clamp based on two control bytes: $C6 (a mode flag) and $C5 (the Y coordinate relative to a reference). Despite sharing the same logical structure, they use different branch mnemonics. Do not assume one routine's pattern applies to another — verify each branch byte explicitly.

The three distinct orderings in the cluster are:

BCS/BPL (type 3+ renderer, Sub_C73A): Carry is tested first, sign second. This ordering is used when large 6-tile sprites enter the clamp path with carry already set from a prior comparison; the carry check eliminates most cases without needing a sign test.

BPL/CMP/BCS (high-state init: Sub_BCDC, Sub_C2BF): Sign is tested first (BPL to the positive path), then a compare against $E0 followed by BCS. No BMI-split. This ordering is safe for high-state init because the raw table values are always bounded; the simple sign-then-carry sequence suffices.

BMI-split (low-state init: Sub_BA65, Sub_BFF2): The positive path has an additional conditional split at its start. After BPL branches to the positive handler, a second BMI instruction immediately skips past the clamp comparison for small positive Y values — a BMI-split. This is present in both low-state routines (BA65 for type 1, BFF2 for types 2/3+) and absent in both high-state routines (BCDC for type 1, C2BF for types 2/3+). The staging buffer Y values that enter the low-state path can be negative-looking two's-complement values that the raw comparison would mishandle; the BMI-split screens these out before the CMP/BCS path runs.

The BPL/BMI dispatch on $C5 is also not uniform: Sub_B788, Sub_B8CA, and Sub_BA65 use BPL to reach the positive (C5 < $80) path, while Sub_C73A, Sub_BCDC, and Sub_BFF2 use BMI to reach the negative (C5 ≥ $80) path. Same logical signal, opposite dispatch direction.

OAM X-pos helper (Sub_C6E7)

Sub_C73A (type 3+ renderer) calls Sub_C6E7 six times, once per tile group of four tiles. Sub_C6E7 reads the X positions of four adjacent tiles, computes the 9th-bit overflow for each (whether the tile's X coordinate exceeds 255), and packs all four overflow bits into a single OAM attribute byte — the standard SNES OAM "high table" format. It writes the X low bytes to the staging buffer ($7F:4BC0/4BC8/4BD0/4BD8) and returns the packed attribute byte in A.
